1. Executive Summary & Infrastructure Automation Imperative
In the preceding units of the Careertiq curriculum, software engineering teams successfully
transformed an enterprise business concept into an Agile product roadmap, engineered a modular
Python/Flask microservice, established continuous automated testing via Pytest, and containerized the
runtime using Docker and Kubernetes. However, in enterprise production, writing robust application
code is only half the software lifecycle equation. 
Before any application can serve customer traffic, organizations must provision and maintain complex
supporting infrastructure: virtual networks, subnets, routing tables, security firewalls, cloud compute
instances, storage volumes, OS-level dependencies, runtime daemons, reverse proxies, and backup
stores. Historically, infrastructure operations relied on manual configuration—commonly referred to in
industry as "ClickOps" or manual server administration via SSH. 
Manual administration introduces critical points of failure: protracted provisioning times, unrecorded
human errors, security misconfigurations, and severe configuration drift between staging and
production environments. Unit 4 introduces Infrastructure as Code (IaC) and Configuration
Management to automate the complete infrastructure lifecycle. Using the Enterprise Smart
Library Management Platform as the reference case study, this document demonstrates how
modern software organizations declare cloud infrastructure via Terraform and automate server
configuration via Ansible on AWS. 
 CORE ARCHITECTURAL OBJECTIVE
Eliminate manual server setup through declarative Infrastructure as Code (Terraform) and
idempotent Configuration Management (Ansible). By codifying the infrastructure lifecycle,
organizations achieve 100% environment reproducibility, zero configuration drift, immutable audit
trails, and automated zero-touch server provisioning.

2.2 Multi-Tier Environment Variations
Infrastructure requirements differ across lifecycle environments. The automation architecture must
accommodate: 
Development Environment: Optimized for rapid developer feedback and minimal cost. Utilizes
single Availability Zone (AZ) deployment, ephemeral storage, and relaxed security groups for local
testing.
Testing & Staging Environment: 100% replica of production. Executes automated CI/CD
integration tests, load tests, and security vulnerability scans.
Production Environment: High availability, multi-AZ resilience, Elastic IP binding, encrypted S3
backups, strict least-privilege IAM roles, and automated alerting.

3.1 Architectural Layer Breakdown
Network Isolation Layer: The platform resides within a custom AWS Virtual Private Cloud (VPC)
assigned the CIDR block 10.0.0.0/16. An Internet Gateway (IGW) is attached to the VPC to enable
bidirectional internet communication. A Public Subnet (10.0.1.0/24) hosts the compute instance,
with default routes (0.0.0.0/0) directed to the IGW.
Security & Ingress Layer: A stateful AWS Security Group acts as a virtual firewall. Ingress traffic
is restricted to Port 22 (SSH administrator access), Port 80 (Nginx HTTP web traffic), and Port 5000
(direct application access). Outbound egress is open to allow APT updates and Docker image pulls.
Compute & Runtime Layer: An AWS EC2 instance running Ubuntu 22.04 LTS executes Docker
Engine. Inside Docker, the Enterprise Smart Library container runs isolated, exposing port 5000.
Nginx functions as a high-performance reverse proxy on Port 80, buffering client requests and
forwarding traffic to the container.
Persistent Storage & State Layer: An AWS S3 bucket maintains versioned, encrypted backups
of library transactions. Concurrently, S3 and AWS DynamoDB provide remote state storage and
distributed locking for Terraform execution.
4. Infrastructure as Code (IaC) with HashiCorp Terraform
Infrastructure as Code (IaC) is the practice of managing and provisioning computing infrastructure
through machine-readable definition files rather than physical hardware configuration or interactive
GUI tools. HashiCorp Terraform is the industry-standard cloud-agnostic IaC engine.

4.1 Core Concepts and Principles of Terraform
Declarative Syntax (HCL): HashiCorp Configuration Language allows engineers to define the 
desired end state of infrastructure. The engineer specifies what resources should exist, and
Terraform calculates how to achieve that state.
Terraform Providers: Plugins that interact with cloud platforms via official APIs. For AWS, the 
hashicorp/aws provider translates HCL declarations into AWS REST API requests.
State Management (terraform.tfstate): Terraform records resource metadata, dependencies, and
IDs in a state file. This state file serves as the single source of truth mapping declared resources to
real-world cloud objects.
State Locking & Concurrency: In team environments, concurrent Terraform executions can
corrupt the state file. Terraform integrates with AWS DynamoDB to enforce distributed mutex
locking during operations.

5. Configuration Management with Ansible
While Terraform provisions cloud fabric (hardware, networking, instances), it is not designed for
granular operating system and software configuration. That task belongs to Configuration
Management tools such as Ansible. 
Figure 5.1: Ansible Agentless Control Node Architecture & Modular Role Execution
5.1 Why Ansible? Key Architectural Advantages
Agentless Architecture: Unlike legacy tools (Puppet, Chef) that require proprietary daemons
running on target servers, Ansible operates over standard OpenSSH. Target servers require only a
Python interpreter.
Push-Based Model: The Ansible Control Node pushes configurations directly to target hosts on
demand, eliminating client pull delays and central server load.
Idempotency: An operation is idempotent if executing it multiple times produces the exact same
outcome without unintended side effects. If a package (e.g., Docker) is already installed, Ansible
reports ok and skips reinstallation.
Human-Readable YAML: Playbooks and roles are declared in straightforward YAML syntax,
facilitating code reviews and cross-team collaboration.
5.2 Modular Ansible Roles Hierarchy
Enterprise configurations are structured into reusable Roles. For the Smart Library Platform: 
roles/common: Updates APT repository caches, installs system utilities (curl, git, jq), and configures
UFW firewall.
roles/docker: Adds official Docker GPG keys, installs Docker CE and containerd, enables systemd
daemons, and adds non-root users to the docker security group.
roles/nginx: Installs Nginx, generates dynamic reverse proxy configurations via Jinja2 templates,
and proxies Port 80 to container Port 5000.
roles/library_app: Deploys the containerized application artifact from Unit 3, mounts persistent
database directories, launches the container with restart policies, and verifies health endpoints.

6.1 The Orchestration Handoff Mechanism
The central engineering challenge is connecting the dynamic outputs of Terraform (such as randomly
assigned AWS public IP addresses) to Ansible's static inventory. Modern DevOps solves this via
automated templating: 
# Automated Handshake Sequence:
1. Terraform provisions EC2 instance and outputs: app_server_public_ip = "54.210.88.14"
2. CI pipeline or wrapper script queries: terraform output -raw app_server_public_ip
3. Output dynamically populates Ansible inventory:
 [library_servers]
 library-host ansible_host=54.210.88.14 ansible_user=ubuntu
4. Ansible executes playbook against newly created host via SSH.

7.1 Achieving 100% Parity via Code
Terraform Workspaces: A single Terraform codebase defines infrastructure across environments
by switching workspaces: terraform workspace select dev vs. prod. Variables dynamically adjust
instance types and replica counts while maintaining identical architecture.
Ansible Group Variables: Environment-specific parameters (e.g., database connection strings,
logging verbosity) reside in group_vars/dev.yml and group_vars/prod.yml, while tasks remain
completely identical.
